The Rise of Software Defined Networking (SDN)

Chapter 1 — Network Industry Trends

What problem existed before SDN?

Traditional networks had a major problem: every router and switch was completely independent and self-contained. If you wanted to change how traffic flows, you had to log into each device one by one and manually configure it using vendor-specific CLI commands. This was slow, error-prone, and hard to scale.

💡 Think of it this way

Imagine if every traffic light in a city had its own brain and could never talk to a central control system. To change traffic flow for an emergency, you'd have to physically go to every single traffic light and reprogram it. That's what traditional networking looked like. SDN is like installing a central traffic control room that manages all lights from one place.

The Control Plane vs. Data Plane

Every network device has two key parts working inside it:

🧠 Control Plane

The "brain" — decides WHERE traffic should go. Runs routing protocols like OSPF, BGP. Makes forwarding decisions.

⚡ Data Plane

The "muscles" — actually moves the packets. Uses hardware ASICs to forward traffic at line speed based on control plane decisions.

In traditional networking, both planes live inside the same device. SDN separates them — the control plane moves to a central SDN Controller, while devices only handle the data plane.

OpenFlow — The First SDN Protocol

OpenFlow was developed by Martin Casado during his PhD at Stanford University. It is the protocol that first made SDN possible by allowing a controller to directly program the flow tables inside network hardware. Think of flow tables as a lookup table that tells the device: "if you see traffic with destination IP X, forward it out port Y."

📌 Key Fact

OpenFlow decouples the control plane from the data plane. It communicates with the hardware's Forwarding Information Base (FIB) to tell devices exactly how to forward packets — in a vendor-neutral way, without waiting for proprietary hardware upgrades.

OpenFlow also supports a hybrid mode where it runs alongside traditional forwarding. If there's no matching OpenFlow rule, the device falls back to its normal routing table. This made adoption easier.

What IS Software Defined Networking?

SDN is a broader architectural approach — not just a single protocol. The key idea is centralizing intelligence. The SDN Controller has a global view of the entire network (called a "network-wide view"), and it pushes configurations down to all devices. Applications can talk to the controller via "northbound APIs" and the controller talks to devices via "southbound APIs" like OpenFlow.

🔼 Northbound API

Used by applications to talk to the SDN controller (e.g., a business app requesting certain traffic priorities).

🔽 Southbound API

Used by the controller to program network devices (e.g., OpenFlow pushes flow rules into switches).

Network Automation

Chapter 2 — Why Automate, Types of Automation, SNMP to APIs, SDN Era

Why Network Automation?

Most people think automation = doing things faster. That's true, but speed is not the only — or even the most important — reason. The textbook explains three core reasons:

🏗️ Simplified Architectures

Automation forces you to design cleaner, consistent networks. No more "snowflake" devices with one-off configs. Every device becomes standardized and repeatable.

🎯 Deterministic Outcomes

A script does exactly what you tell it, every single time. Humans make typos; scripts don't. The same automation run on 500 devices produces the same result every time.

🚀 Business Agility

Business needs networks to respond fast. Automation lets you provision new services in minutes instead of weeks, giving the business a competitive edge.

💡 Real-world analogy

Think about a factory assembly line vs. handmade products. A handmade approach is flexible but inconsistent and slow. An assembly line is fast, consistent, and scalable — though it requires upfront design. Network automation is your assembly line.

Types of Network Automation Tasks

The textbook identifies several key areas where automation provides value:

1
Device Provisioning

Automatically configure new devices when they join the network — Day 0 (initial setup) and Day 1 (initial deployment) configurations pushed automatically instead of logging into each device.

2
Data Collection

Automatically gather operational data (interface statistics, routing tables, BGP neighbors) from all devices at scale. Impossible to do manually across hundreds of devices.

3
Migrations

Moving from one platform/vendor to another. Automation can translate configs from one format to another and deploy them, reducing human error during high-risk migrations.

4
Configuration Management

Ensure devices always have the correct configuration. If something drifts (someone made a manual change), automation detects and corrects it — "configuration drift" management.

5
Compliance & Reporting

Automatically verify that all devices comply with security policies (e.g., no Telnet enabled, all ports use SSH). Generate compliance reports automatically.

6
Troubleshooting

Automated diagnostics can detect, correlate, and even fix common issues — like auto-bouncing a port that's in error-disabled state, or identifying which link caused a BGP flap.

Evolving from SNMP to Device APIs

For decades, SNMP (Simple Network Management Protocol) was the only way to programmatically interact with network devices. SNMP was designed for monitoring — reading counters and status. It was never great at configuration. Device APIs are a massive improvement:

FeatureSNMPModern Device APIs
Primary UseMonitoring onlyMonitoring + Configuration + Operations
Data FormatOIDs (cryptic numbers)JSON, XML (human-readable)
Ease of UseComplex MIB navigationSimple HTTP calls or Python libraries
ConfigurationVery limitedFull configuration capability
Error HandlingMinimalStructured error responses

Network Automation in the SDN Era

You might wonder: if SDN has a central controller, do we still need automation tools? The answer is yes. Even with an SDN controller, you still need to: configure the controller itself, manage devices that aren't SDN-capable, handle multi-vendor environments, and build workflows that span multiple systems. Automation tools complement controllers — they don't replace each other.

Linux for Network Automation

Chapter 3 — Linux Distributions, Filesystem, Networking in Linux

Why Linux for Network Engineers?

Linux is everywhere in modern networking: it powers network operating systems (Cumulus Linux, SONiC), automation tools (Ansible runs on Linux), SDN controllers, and cloud infrastructure. Most automation scripts are developed and run on Linux. The textbook says: learning Linux is no longer optional for next-generation network engineers.

💡 Why Linux specifically?

Linux is free, open-source, stable, and runs on everything from a Raspberry Pi to a 1000-server data center. Every major automation framework (Ansible, Salt, StackStorm) runs natively on Linux. It's the lingua franca of DevOps and infrastructure automation.

Linux Distributions

A Linux "distribution" (distro) is a complete package: Linux kernel + tools + package manager. The textbook covers three main families:

🎩 Red Hat Family

RHEL, CentOS, Fedora. Enterprise-focused. Uses yum/dnf for packages. RHEL is paid/supported; CentOS was the free clone. Common in enterprise data centers.

🐧 Debian Family

Debian, Ubuntu. Uses apt package manager. Ubuntu is extremely popular for desktops and automation dev environments. Great for beginners.

🔧 Others

Arch, Gentoo, Alpine. Each has a purpose — Alpine is tiny and used in Docker containers; Arch is for advanced users wanting full control.

Networking in Linux

The textbook covers Linux networking in depth. Linux treats everything as a file, including network interfaces. Key networking concepts:

# Viewing and configuring interfaces (modern method)
ip addr show            # Show all IP addresses
ip addr show eth0        # Show eth0 interface
ip link set eth0 up      # Bring interface up
ip link set eth0 down    # Bring interface down
ip addr add 10.0.0.1/24 dev eth0  # Add IP address

# Routing
ip route show            # Show routing table
ip route add 0.0.0.0/0 via 10.0.0.254  # Add default route

# Diagnostics
ping 8.8.8.8             # Test connectivity
traceroute google.com    # Trace path to host
ss -tunlp               # Show listening ports (modern netstat)
tcpdump -i eth0          # Capture packets on eth0

Linux can also act as a router (IP forwarding) or a bridge (software switch). These are essential for virtual network environments and NFV.

💚 Exam Tip

The textbook uses ip commands (iproute2 package) which are modern replacements for the older ifconfig and route commands. Know both — older commands still appear on many devices.

Python for Network Engineers

Should Network Engineers Learn to Code?

The textbook's answer is clear: yes, absolutely. The book argues that network engineers who understand programming will be far more valuable and capable than those who don't. You don't need to become a full software developer — but you need enough Python to automate repetitive tasks, interact with APIs, and process network data.

💡 Why Python specifically?

Python has become the dominant language in network automation because it's easy to learn, has a massive ecosystem of networking libraries (Netmiko, NAPALM, Nornir), is platform-independent, and is supported by almost every vendor's API. Cisco, Juniper, Arista — they all have Python libraries.

Lists — Working with Multiple Values

Lists store multiple values in order. Perfect for lists of devices, interfaces, IP addresses:

# Creating a list of routers
routers = ["R1", "R2", "R3"]

# Accessing elements (0-indexed)
print(routers[0])    # R1
print(routers[-1])   # R3 (last element)

# Adding elements
routers.append("R4")
print(routers)       # ['R1', 'R2', 'R3', 'R4']

# List slicing
print(routers[0:2])   # ['R1', 'R2']

Dictionaries — Key-Value Data

Dictionaries store data as key-value pairs — extremely useful for representing device configurations:

# A dictionary representing a device
device = {
    "hostname": "Router-1",
    "ip": "10.0.0.1",
    "vendor": "Cisco",
    "os": "IOS-XE",
    "port": 22
}

# Accessing values
print(device["hostname"])    # Router-1
print(device.get("ip"))       # 10.0.0.1

# Adding/updating keys
device["location"] = "DC1"

# Iterating over a dictionary
for key, value in device.items():
    print(f"{key}: {value}")

Understanding Containment

Python uses the in keyword to check if something exists inside a container (list, dict, string). This is called containment:

vlans = [10, 20, 30, 40]
print(20 in vlans)        # True
print(99 in vlans)        # False

config = "interface GigabitEthernet0/1"
print("GigabitEthernet" in config)  # True

Loops

Loops let you repeat actions. Crucial for applying the same operation to multiple devices:

# for loop — iterate over a list
devices = ["R1", "R2", "R3"]
for device in devices:
    print(f"Connecting to {device}...")
# Output:
# Connecting to R1...
# Connecting to R2...
# Connecting to R3...

# while loop — repeat until condition is false
count = 0
while count < 3:
    print(f"Retry attempt {count}")
    count += 1

Functions

Functions let you package reusable code. Instead of writing the same connection logic 50 times, write it once as a function:

def get_device_info(hostname, ip, vendor="Unknown"):
    """Returns a formatted device info string"""
    return f"Device: {hostname} | IP: {ip} | Vendor: {vendor}"

# Calling the function
print(get_device_info("R1", "10.0.0.1", "Cisco"))
print(get_device_info("SW1", "10.0.0.2"))  # Uses default vendor

Data Formats & Data Models

Chapter 5 — YAML, XML, JSON, YANG

Introduction to Data Formats

When two programs need to exchange data, they must agree on a standard format — just like how people from different countries need a common language to communicate. In networking, APIs send and receive structured data. The three most common formats are YAML, XML, and JSON. Each has strengths for different use cases.

💡 Think of it like this

Imagine you need to tell someone about a network device. You could write it as a paragraph (hard for computers to parse), as a filled-out form with labeled fields (structured — that's data formats!), or as an Excel spreadsheet. Data formats are the "forms" computers use to exchange information.

YAML — Human-Readable Data

YAML (YAML Ain't Markup Language) uses indentation to show structure. It's designed to be easy for humans to read and write. Ansible uses YAML extensively for its playbooks and inventory files.

YAML Basics:

# YAML uses indentation (spaces, NOT tabs!) for structure
# Key-value pairs (like a dictionary)
hostname: Router-1
ip: 10.0.0.1
vendor: Cisco
enabled: true

# Lists (use dashes)
vlans:
  - 10
  - 20
  - 30

# Nested structure (like a dict inside a dict)
interfaces:
  - name: GigabitEthernet0/1
    ip: 192.168.1.1
    mask: 255.255.255.0
    status: up
  - name: GigabitEthernet0/2
    ip: 192.168.2.1
    mask: 255.255.255.0
    status: down

Working with YAML in Python:

import yaml

# Reading YAML from a file
with open("devices.yaml") as f:
    data = yaml.safe_load(f)  # Returns Python dict/list

print(data["hostname"])     # Router-1
print(data["vlans"])        # [10, 20, 30]

# Writing Python data to YAML
device = {"hostname": "R2", "ip": "10.0.0.2"}
with open("output.yaml", "w") as f:
    yaml.dump(device, f)

XML — Extensible Markup Language

XML uses tags (like HTML) to structure data. It's been around since 1998 and is used heavily in NETCONF, which is the main protocol for configuring network devices programmatically. XML is verbose but very structured and supports schemas (XSD) to validate data.

<!-- XML example: a network device in XML format -->
<device>
  <hostname>Router-1</hostname>
  <ip>10.0.0.1</ip>
  <vendor>Cisco</vendor>
  <interfaces>
    <interface>
      <name>GigabitEthernet0/1</name>
      <ip>192.168.1.1</ip>
      <status>up</status>
    </interface>
  </interfaces>
</device>

XSD (XML Schema Definition) — defines rules for what a valid XML document must look like. Think of it as a template that says "this XML must have a hostname field, an IP field in x.x.x.x format, etc."

XSLT (Extensible Stylesheet Language Transformations) — transforms XML from one format to another. For example, converting device config XML into a human-readable HTML report, or converting vendor-specific XML to a standard format.

JSON — JavaScript Object Notation

JSON is currently the most popular data format for REST APIs. It's similar to Python dictionaries and is easy to read. Virtually every modern network device API (Cisco NX-API, Arista eAPI, etc.) uses JSON.

// JSON Example: Same device in JSON format
{
  "hostname": "Router-1",
  "ip": "10.0.0.1",
  "vendor": "Cisco",
  "vlans": [10, 20, 30],
  "interfaces": [
    {
      "name": "GigabitEthernet0/1",
      "ip": "192.168.1.1",
      "status": "up"
    }
  ]
}

YANG — Data Modeling for Networks

YANG (Yet Another Next Generation) is a data modeling language designed specifically for network configuration and state data. While YAML/XML/JSON describe how data is formatted, YANG describes what the data means — what fields are required, what types they are, how they relate to each other.

💡 YANG vs. other formats

Think of JSON/XML as a form. YANG is like the official government specification that defines exactly what fields the form must have, what type of data goes in each field, and what values are valid. YANG is the blueprint; JSON/XML is the filled-out form.

YANG models are used with NETCONF and RESTCONF to ensure devices from different vendors accept the same data structure. The IETF and OpenConfig working groups have created standard YANG models that vendors implement. A simple YANG model looks like:

// Simplified YANG model for an interface
module interfaces {
    container interfaces {
        list interface {
            key "name";
            leaf name {
                type string;
            }
            leaf ip-address {
                type string;
            }
            leaf status {
                type enumeration {
                    enum up;
                    enum down;
                }
            }
        }
    }
}

Network Configuration Templates with Jinja2

Chapter 6 — Why templates, Jinja basics, conditions, loops, filters

Why Use Templates?

Imagine you need to configure 100 routers with the same BGP settings, but each router has a different hostname, IP address, and AS number. Without templates, you'd write 100 unique config files manually — tedious and error-prone. With templates, you write ONE template and fill in the variable data automatically.

💡 Real-world analogy

Think of a mail merge in Word. You have one letter template with fields like "Dear [Name]" and a spreadsheet with 500 names. The mail merge fills in each name automatically. Jinja2 does this for network configurations — one template, many devices.

Dynamically Inserting Data into Jinja Templates

In Jinja2, variables are placed inside {{ }} (double curly braces). The template engine replaces these with actual values when rendered:

{# This is a Jinja2 template for a basic router config #}
{# Variables are in {{ double curly braces }} #}

hostname {{ hostname }}
!
interface {{ interface }}
 ip address {{ ip_address }} {{ subnet_mask }}
 no shutdown
!
router bgp {{ bgp_as }}
 neighbor {{ neighbor_ip }} remote-as {{ neighbor_as }}

Rendering a Jinja Template in Python

from jinja2 import Environment, FileSystemLoader

# Set up Jinja environment to load templates from current directory
env = Environment(loader=FileSystemLoader("."))
template = env.get_template("router_template.j2")

# Data to fill into the template
data = {
    "hostname": "Router-1",
    "interface": "GigabitEthernet0/1",
    "ip_address": "10.0.0.1",
    "subnet_mask": "255.255.255.0",
    "bgp_as": 65001,
    "neighbor_ip": "10.0.0.2",
    "neighbor_as": 65002
}

# Render the template
config = template.render(data)
print(config)

# Save to file
with open("Router-1.cfg", "w") as f:
    f.write(config)

Conditions and Loops in Jinja

Jinja supports if/else and for loops, making templates very powerful:

{# Jinja conditions — use {% %} for logic #}

{% if ospf_enabled %}
router ospf 1
 network {{ ospf_network }} area 0
{% endif %}

{% if bgp_as is defined %}
router bgp {{ bgp_as }}
{% else %}
! No BGP configured
{% endif %}

{# Jinja for loop — generate config for multiple interfaces #}

{% for interface in interfaces %}
interface {{ interface.name }}
 ip address {{ interface.ip }} {{ interface.mask }}
 {% if interface.shutdown %}
 shutdown
 {% else %}
 no shutdown
 {% endif %}
!
{% endfor %}

Jinja Filters

Filters transform variables inline using the pipe | symbol. Very handy for formatting:

{# Common Jinja filters #}

{# upper/lower — change case #}
{{ hostname | upper }}          {# ROUTER-1 #}
{{ vendor | lower }}            {# cisco #}

{# default — use fallback if variable is undefined #}
{{ location | default("Unknown") }}

{# join — join a list with a separator #}
{{ vlans | join(", ") }}        {# 10, 20, 30 #}

{# length — count items #}
{{ interfaces | length }}       {# 4 #}

{# replace — string replacement #}
{{ hostname | replace("-", "_") }}
💚 Why This Matters

Templates + data files (YAML) + a Python rendering script = a complete network configuration generation system. You define all your device parameters in YAML, and the script generates ready-to-push configs for all devices at once. This is how large-scale network automation works in real enterprises.

Network APIs

Chapter 7 — HTTP-Based APIs (REST & Non-REST), NETCONF, cURL, Postman

What is an API?

An API (Application Programming Interface) is a defined way for programs to communicate. In networking, APIs let your scripts and tools talk to network devices without CLI. Instead of SSHing in and typing commands, you send structured requests over HTTP or other protocols and get structured responses back.

💡 Restaurant analogy

An API is like a waiter at a restaurant. You (the application) don't go into the kitchen (the device) directly. You give your order to the waiter (API) in a specific format (the menu), and the waiter brings back the result. The kitchen doesn't need to know or care who you are — it just processes orders in a standard format.

HTTP-Based APIs — RESTful

REST (Representational State Transfer) is an architectural style for building APIs. RESTful APIs use standard HTTP methods and URLs. They're stateless (each request is independent) and use JSON or XML for data. Most modern network devices and SDN controllers expose RESTful APIs.

The four HTTP methods you must know:

HTTP MethodOperationNetwork Example
GETRetrieve data (read-only)Get interface status, get routing table
POSTCreate new resourceAdd a new VLAN, create a BGP neighbor
PUTReplace/update resourceReplace entire interface config
DELETERemove resourceDelete a VLAN, remove a route

HTTP Response Codes:

CodeMeaning
200 OKSuccess

400 Bad RequestYour request has an error (bad syntax)
401 UnauthorizedAuthentication required/failed
404 Not FoundResource doesn't exist
500 Internal Server ErrorDevice/server side error

Exploring APIs with cURL

cURL is a command-line tool for making HTTP requests — great for testing APIs before writing Python code:

# Basic GET request
curl -X GET https://device-ip/api/v1/interfaces

# GET with authentication headers
curl -X GET \
     -H "Content-Type: application/json" \
     -H "Accept: application/json" \
     -u admin:password \
     https://192.168.1.1/api/v1/vlans

# POST to create a new VLAN

     -H "Content-Type: application/json" \

Using the Python requests Library

The requests library is the standard Python library for making HTTP API calls:

import requests
import json

# Disable SSL warnings (for lab environments)
requests.packages.urllib3.disable_warnings()

# Basic GET request
url = "https://192.168.1.1/api/v1/interfaces"
headers = {
    "Content-Type": "application/json",
    "Accept": "application/json"
}
response = requests.get(
    url,
    headers=headers,
    auth=("admin", "password"),
    verify=False  # ignore SSL in labs
)

# Check if request was successful
if response.status_code == 200:
    data = response.json()  # Parse JSON response
    print(json.dumps(data, indent=2))
else:
    print(f"Error: {response.status_code}")

Using Cisco NX-API

Cisco Nexus switches expose a non-RESTful API called NX-API. It accepts CLI commands inside a JSON payload and returns the output as structured JSON — essentially a "JSON-ified CLI":

import requests, json

url = "http://10.0.0.1/ins"
headers = {"content-type": "application/json"}
payload = {
    "ins_api": {
        "version": "1.0",
        "type": "cli_show",
        "chunk": "0",
        "sid": "1",
        "input": "show version",  # CLI command here
        "output_format": "json"
    }
}
response = requests.post(url, json=payload,
                         auth=("admin", "password"),
                         headers=headers)
print(response.json())

NETCONF — Network Configuration Protocol

NETCONF is a protocol specifically designed for network device configuration. It runs over SSH, uses XML for data (with YANG models defining the structure), and provides transactional operations — meaning changes either fully succeed or are rolled back. This is far safer than manual CLI changes.

NETCONF Protocol Stack:

LayerTechnologyRole
ContentYANG models (XML data)What data is being configured
Operationsget, get-config, edit-config, commitWhat action to perform
MessagesRPC (Remote Procedure Call)How to package the operation
TransportSSH (port 830)Secure transport layer

Using ncclient (NETCONF Python library):

from ncclient import manager

# Connect to a NETCONF device
with manager.connect(
    host="192.168.1.1",
    port=830,
    username="admin",
    password="password",
    hostkey_verify=False
) as m:

    # Get the running configuration
    running_config = m.get_config(source="running")
    print(running_config)

    # Edit configuration using XML payload
    config_xml = """
    <config>
      <interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
        <interface>
          <name>GigabitEthernet1</name>
          <description>Configured by NETCONF</description>
        </interface>
      </interfaces>
    </config>
    """
    m.edit_config(target="candidate", config=config_xml)
    m.commit()  # Commit the change (like a database commit)

Using Netmiko for SSH Automation

Netmiko is a Python library that simplifies SSHing into network devices and sending CLI commands. It handles the vendor-specific quirks of hundreds of device types. This is the most approachable way to start automating existing networks:

from netmiko import ConnectHandler

# Device connection parameters
device = {
    "device_type": "cisco_ios",  # Device type (netmiko knows the quirks)
    "host": "192.168.1.1",
    "username": "admin",
    "password": "password",
}

# Connect and send commands
with ConnectHandler(**device) as net_connect:
    # Send show command and get output
    output = net_connect.send_command("show ip interface brief")
    print(output)

    # Send configuration commands
    config_commands = [
        "interface GigabitEthernet0/1",
        "description Automated Config",
        "no shutdown"
    ]
    net_connect.send_config_set(config_commands)

# Automate across multiple devices
routers = ["192.168.1.1", "192.168.1.2", "192.168.1.3"]
for router_ip in routers:
    device["host"] = router_ip
    with ConnectHandler(**device) as conn:
        output = conn.send_command("show version")
        print(f"{router_ip}: {output[:50]}")

Ansible — The Most Popular Network Automation Tool

Ansible is agentless — it connects to devices via SSH (or APIs) and pushes configuration. No software needs to be installed on the managed devices. This makes it great for network automation since most network devices can't run arbitrary software.

1
Inventory File

Ansible starts with an inventory file that lists all your devices. Can be in INI or YAML format. Groups devices by role or location.

2
Playbook

A YAML file that describes tasks to perform on devices. Consists of Plays (which devices?) and Tasks (what to do?). Each task uses a module.

3
Modules

Pre-built units of work. ios_command sends commands to Cisco IOS. eos_config configures Arista EOS. Hundreds of network modules exist.

# inventory.ini — Ansible inventory file
[routers]
R1 ansible_host=10.0.0.1
R2 ansible_host=10.0.0.2
R3 ansible_host=10.0.0.3

[switches]
SW1 ansible_host=10.0.1.1

[all:vars]
ansible_user=admin
ansible_ssh_pass=password
ansible_network_os=ios
# playbook.yml — Ansible Playbook
---
- name: Gather and Display Router Info      # Play name
  hosts: routers                            # Which inventory group
  gather_facts: no                          # Skip default fact gathering

  tasks:
    - name: Get interface status            # Task name
      ios_command:                          # Module to use
        commands:
          - show ip interface brief
      register: int_output                  # Store output in variable

    - name: Print interface output
      debug:
        var: int_output.stdout_lines

    - name: Configure NTP server
      ios_config:
        lines:
          - ntp server 10.0.0.100

    - name: Save configuration
      ios_command:
        commands:
          - write memory
# Run the playbook
ansible-playbook -i inventory.ini playbook.yml

# Run with verbose output
ansible-playbook -i inventory.ini playbook.yml -v

# Run only on specific hosts
ansible-playbook -i inventory.ini playbook.yml --limit R1
📌 How Ansible Works

Ansible is idempotent — running the same playbook multiple times produces the same result. It checks current state first, and only makes changes if needed. This is the "desired state" model: describe what you want, Ansible figures out how to get there.

Salt — High-Scale Event-Driven Automation

Salt uses a master-minion architecture. A Salt Master server manages many Salt Minions (agents running on managed devices). For network devices that can't run a minion, Salt uses a "proxy minion" — a process on the master that represents the device.

🏛️ Salt Master

Central server that sends commands, stores configuration states, and processes events. Manages all minions from one place.

🤖 Salt Minion

Agent running on managed devices. Connects to master, receives commands, reports state. For network devices: proxy minion runs on master.

⚡ Salt Bus

Event bus (using ZeroMQ) that connects master to minions. Extremely fast — Salt can manage thousands of devices simultaneously.

# Run a command on all minions (like ansible ad-hoc)
salt '*' test.ping

# Run on specific minion
salt 'router1' network.interfaces

# Apply a state (Salt's version of Ansible playbooks)
salt 'router1' state.apply ntp_config

# Get current interface info
salt 'router1' net.interfaces

Salt's event-driven infrastructure is particularly powerful — devices can fire events (like "interface went down") and Salt can automatically react (like "notify team, bring up backup link").

StackStorm — Event-Driven Network Automation

StackStorm is designed specifically for event-driven automation — "if this happens, do that." It's like a network automation IFTTT (If This Then That). Rather than just running scheduled tasks, StackStorm watches for events and responds to them intelligently.

📡 Sensors

Watch for events from external systems — monitoring tools, SNMP traps, webhooks. The "ears" of StackStorm.

⚡ Triggers

Fired when a sensor detects something. E.g., "interface-down trigger" fired when monitoring detects an interface failure.

📋 Rules

Define what to do when a trigger fires. Match triggers to actions. E.g., "if interface-down trigger, run failover-action."

🎬 Actions

The actual work — run scripts, call APIs, SSH to devices, notify teams. Multiple actions can be chained into Workflows.

# StackStorm rule (YAML) — react to an event
---
name: auto_failover_on_interface_down
description: Automatically activate backup link when primary fails
enabled: true

trigger:
  type: network.interface_down    # Triggered by this event

criteria:                         # Only act if these conditions are met
  trigger.interface_name:
    type: equals
    pattern: GigabitEthernet0/1

action:
  ref: network.activate_backup_link  # Run this action
  parameters:
    device: "{{ trigger.hostname }}"
    backup_interface: GigabitEthernet0/2

💚 Exam Summary — Tools Comparison

Ansible: Agentless, push model, YAML playbooks, SSH transport, great for beginners. Salt: Agent-based (master-minion), fast ZeroMQ bus, event-driven capability, best for large scale. StackStorm: Pure event-driven (Sensors → Triggers → Rules → Actions), responds to real-time network events automatically.
